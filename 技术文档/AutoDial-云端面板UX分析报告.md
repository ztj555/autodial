## 一、总体结论

面板经过 v4.18 → v4.26 多轮针对性迭代，**在"管理员后台"这个品类里成熟度已经很高**：
信息层级、快捷操作、错误分层、防误触、状态保持等大部分常见坑都已修掉，且代码里留有大量
"为什么这么改"的注释，可维护意识好。

当前剩余问题集中在三类：

1. **一致性残留**——v4.24 改版目标（全站别名、默认今天、分页统一）有个别漏网点；
2. **登录/会话体验**——会话生命周期对用户完全不可见，重启即全员掉线且无感知；
3. **数据通路的效率**——15s 轮询 + 串行请求 + 前端聚合，属于"能用但天花板低"的架构。

没有发现"反人类"级别的交互缺陷。以下按 做得好 → 问题清单（分级）→ 技术优化空间 → 不建议做 展开。

## 四、交互/技术层优化空间（架构视角）

### 4.1 轮询 → WebSocket 推送（最大的天花板项）

现状：面板全部数据靠 15s `setInterval` 轮询，每轮首页打 5 个接口；而服务端本身就有
WebSocket 基础设施（手机/PC 端全走 WS，cloud_relay_v2.py 的 `_push_visit_to_phone` 等推送函数已存在）。

- 收益：在线状态/新登记/新通话**秒级可见**（值班场景"手机掉线"的发现延迟从最长 15s 降到即时）；
  面板请求量下降一个数量级；429 限流压力消失。
- 成本：需要给面板加一个 WS 订阅通道 + 服务端广播点，属于动后端的中型改动。
- 建议：短期先把 P1-7（并行化 + 折叠区懒拉）做掉，轮询架构还能撑很久；WS 化留作数据量/实时性真成为痛点时的大版本项。

### 4.2 请求层小重构

- `window.fetch` 全局包装按"URL 含 `/api/`"注入 token（dashboard.html:1726-1738）：当前无第三方请求所以安全，但属于隐式全局副作用，将来引入任何外部 API（如统计）会被误注入。
- `withToken()` 已是恒等函数（:1740-1744）却仍被 20+ 处调用：读代码的人会以为它做了什么。两者可在下次大改时一并清理。

### 4.3 单文件规模

3209 行单文件、无构建、无组件化。当前"一个人维护 + 注释充分"的前提下**利大于弊**（部署就是 COPY 一个文件），
但页面数或交互复杂度再翻倍时建议拆分为 `dashboard.html + app.js + themes.js`（扩展端已有同样的拆分先例：cs-00~cs-70）。

### 4.4 会话持久化（配合 P0-4）

`_admin_sessions` 落内存意味着每次发版重启 = 全员重新登录。可选方向（按侵入性排序）：
token 表定期写 `visits.db` / 启动时加载；或面板在 401 时自动弹登录框并**保留当前页面与筛选**（现在会 `location.reload()` 回首页，:3173）。

## 五、不建议做的（尊重既有决策，避免重复提议）

《改版方案》§五已明确不做且理由成立的，本报告不翻案：

| 项 | 维持不做的理由 |
|---|---|
| CSP / X-Frame-Options / CORS 收紧 | 自用 + 内网固定 IP，收益低于维护成本 |
| `/api/v1/visits?pin=x` 单 PIN 免鉴权 | 手机端同步的既定设计，动它影响面大 |
| chart.js 换国内镜像 | 天天联网，CDN 失败时图表空白但页面功能不受影响 |
| 主题色值收敛 | 受"主题六处同步"铁律约束，动一处要同步六处 |
| 死常量清理、测试文件归位 | 代码整洁项，不影响使用 |

## 对报告的两处补正

**1. P0-2 不是「改个文案」那么简单——两边改哪边，效果不同。**
报告建议把文案 200 改成 20。但服务端事实是：batch 接口（`cloud_relay_v2.py:2622-2624`）**v4.21 起已支持 POST body**（当初正是为绕开 websockets `MAX_LINE_LENGTH` 8KB 请求行上限才加的），
服务端**无条数上限**，`serve()`（`:3517`）也未设 `max_size` ⇒ 走 websockets 默认 1 MiB。
即"20 条"现在只是客户端遗留的保守值，已非技术约束。两个选项：

- ① 文案改 20：最小改动，但 200 条要跑 10 个来回；
- ② `BATCH_SIZE` 提到 100~200：导入快 5~10 倍。⚠️ **仅对 POST 路径安全**，GET 兼容路径仍受 8KB 限制，不可一起提。

**2. P1-1 是判断题，不是纯 bug——报告的处理方式会牺牲功能。**
报告建议"通话页也默认今天"。但通话页默认"全部"有实用价值：排查一通旧电话时，"今天"会把要找的数据藏起来。
**真正的问题是 chips 无 active 态**（无区间时四个 chip 全不亮，用户看不出当前处于"全部"）。
建议改为：保留"全部"为默认，仅让 `_syncChips` 在无区间时点亮"全部"——成本相同，不牺牲功能。

**3. 分级微调**：P0-3（日志滚动）建议降为 P1——恼人但不影响正确性，且修法极简（判断用户是否已在底部附近再决定是否滚动）。
