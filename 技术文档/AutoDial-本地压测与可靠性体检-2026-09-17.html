二、压测结果

按真实调用方组织 5 个场景，不是拍脑袋打一个端点：poll（面板 15 秒刷新一轮的 6 个请求）、report（手机批量上报）、visit（登记写入）、export（CSV 全量导出）、mixed（24 并发混合）。

先说好消息：两种环境下全部 0 个非 2xx、0 条 database is locked、0 个未捕获异常。 1.43 万条通话、1800 条上门的数据量下，服务端逻辑是稳的。

2.2 根因：不是代码，是这台机器的「文件系统慢区」

先量到单次请求的固定底噪：凡是碰数据库的端点，每个请求固定多花约 150–190 ms；纯内存的 /api/stats 只要 2 ms。而请求里每调一次 _connect_db() 就多一份这份开销（events/log 要 2 次 → 正好是别人的 2 倍）。

再做最小实验，锁定在文件系统：

实验结果
只读打开同一个库（mode=ro）8.3 ms —— 快
读写打开（会创建 -wal/-shm）140–325 ms —— 慢
同目录 / 同盘的副本（换文件名）138 ms —— 一样慢
同一份库放到 %TEMP%6.5 ms —— 快
创建→写→fsync→删除一个 4 KB 文件项目目录/我的文档/下载：约 380 ms　·　%TEMP%：4 ms
结论：你这台机器上，用户目录（Documents / Downloads / Videos / 项目目录）里「新建 + 落盘 + 删除」一个文件要花约 380 ms， 只有 %TEMP% 是正常的 4 ms。SQLite 在 WAL 模式下每个连接都要创建/删除 -wal、-shm， 而中继是每个请求新建一个数据库连接 —— 两者相乘就是你感觉到的「卡」。
  • 这不是项目代码的问题（同一份代码、同一份数据、放到 %TEMP% 就快 6–8 倍）。
  • 也不是 OneDrive（OneDrive 在 C:\Users\EDY\OneDrive，目录没有重解析点）、不是磁盘类型（同盘同 NTFS）。
  • 高度怀疑是杀毒/安全软件的实时文件过滤驱动：症状是「读很快、建/删很慢」、「全用户目录慢、唯独 %TEMP% 快」，这是它的典型指纹。
  • 这解释了为什么 /api/v1/visit 两边一样快：它是唯一被高频连续调用的写端点，连接不断档，-wal 文件一直活着，就不用反复建删。
要不要处理？（建议做）把本地开发库挪出用户目录，例如让 devwatch 把 AUTODIAL_DB_PATH 指到 %LOCALAPPDATA%\autodial-dev\visits.db。改动只在 devwatch.py 一处、不影响打包产物， 本地实例的接口延迟预计直接从 150 ms 掉回 10 ms 级 —— 好处是你以后在本地判断「面板卡不卡」不会被环境骗。
生产服务器（腾讯云 Linux）不受影响：那边建 -wal 是毫秒级。所以不要根据本地的数字去改代码逻辑。

三、不靠谱清单（按风险排序）

P0 · 安全✅ v4.32 已修复设备注册校验可被绕过 —— 公网上任何人能凭空造手机、灌假通话记录

修复状态（v4.32）：已按下方「建议做」补上同一道 _device_registered() 门禁（未改成要求管理员 token，避免打断手机端上报）。 上面 ①–⑦ 的复现脚本原样重跑：③ 由 200 → 403、④⑤ 仍 403、⑥ 伪造设备不再进清单、⑦ 0 条脏记录。 同时验证真实已注册设备的 stats/report / calls/batch / events/log 仍为 200（非回归，用后即还原、数据零残留）。

v4.23 的 Y-1 修复给 calls/batch 和 events/log 加了「设备必须已在云端注册」的校验，本意是堵住伪造上报。 但 /api/v1/stats/report 这个端点既不要管理员身份、也不校验设备是否已注册，却会往 phones 表里插一行设备 —— 于是它成了后门。

实测复现（在本地 35430 上跑的，全程无需任何口令）：

① 未注册设备直接 calls/batch     → HTTP 403 DEVICE_NOT_REGISTERED   ← 防护有效
② 未注册设备 events/log           → HTTP 403                        ← 防护有效
③ 无 token 调 stats/report        → HTTP 200 {"ok":true}            ← 后门：设备被写进库
④ 再调 calls/batch（同一设备）    → HTTP 200 {"inserted":1}          ← 校验被绕过
⑤ 再调 events/log                 → HTTP 200
⑥ 该设备出现在面板「手机管理」清单 → 是（机型「伪造机型」、版本「9.99」）
⑦ 伪造的通话记录已入库

影响：数据可信度。线上部署在公网 35430，任何知道 IP 的人都能批量伪造手机和通话记录，污染首页统计、手机管理清单、「今日通话」。不能拿它执行代码，但足以让报表全不可信。

建议做（改动很小）：给 stats/report 加上和另外两个端点完全一样的 _device_registered() 校验（3 行）。 注意：不能简单改成「要求管理员 token」—— 手机端没有管理凭据，那样会打断正常上报。用同一套「已注册设备」判断即可，语义与设计文档一致。

顺带：修完要确认首次握手的顺序 —— 设备必须先 phone_hello 写进 phones 再上报，这个前提 calls/batch 已经在依赖了，所以不影响正常机。

中 · 数据口径✅ v4.32 已修复同一个「今天」，首页和手机管理页差 7 倍

修复状态（v4.32）：首页已改用 dial_time 区间（与对账页同口径）。 实测 14,306 → 2,006，与 dial_time 区间直算完全相等；与对账页合计 1,970 的 36 条差额已逐台核对， 全部来自一台没有对账快照的备用机（对账页本就不含它），非口径问题。 EXPLAIN QUERY PLAN：旧写法 SCAN → 新写法 SEARCH … USING COVERING INDEX idx_call_records_dial， 单次 3.27 ms → 0.10 ms（首页是 15 秒轮询端点）。
顺带把首页「今日上门」也对齐到列表页口径 COALESCE(NULLIF(visit_time,''),created_at)： 插件端不传 visit_time ⇒ 今天行为完全不变，但批量导入带「上门时间」列时不会再有同类漂移。

实测：首页 /api/status 的「今日通话」= 14,307（修复前）；手机管理页「每日对账」今日合计 = 1,970。

页面SQL 口径含义
首页「今日通话」WHERE date(server_time)=今天入库时间 —— 补传的历史也算今天
手机管理页「每日对账」WHERE dial_time>=今日0点拨打时间 —— 真实的今天

什么时候会真的出错：手机离线几天后补传（这正是「离线补推队列」存在的理由）。那天一补传，首页「今日通话」会把过去几天的量全算进今天，而对账页仍然显示真实值 —— 两个页面对不上，看的人会以为谁在刷数据。

建议做：把首页改成和 phone_daily_stats 同口径（用 dial_time，3 行）。 附带好处：date(server_time) 这种写法用不上任何索引，而 /api/status 是面板每 15 秒轮询一次的端点，数据量再涨就是全表扫。
不改也不影响功能，只是「首页那个数」在补传场景下不准。

中 · 一致性「批量导入」和「手机端登记」算归属的方式不一样

同一个上门记录，两条路进来归属可能不同：

  • 手机端/插件端 /api/v1/visit：按「接待顾问姓名」反查 PIN 来决定归属（v4.29 的语义，代登记归被代的人）—— 已验证正确。
  • 管理员批量导入 /api/v1/visits/batch：直接采信文件里的 pin 字段，完全不看 kefu_tel。

风险：以后从 CRM 导出的表格里，只要 pin 列和 kefu_tel（接待顾问）对不上、或者 pin 为空，就会产生「归属顾问 ≠ 接待顾问」的脏数据，而且面板不会报任何异常 —— 统计立刻错，但没人看得出来。

建议做（做/不做都行）：让批量导入也走同一套「按姓名反查 PIN」的归一化（查不到再回退文件里的 pin）。 如果导入文件的 pin 列本来就是 CRM 的权威值，也可以不改 —— 但要明确「批量导入的归属以文件为准」，别让两套规则并存。

中 · 性能放大每个请求都新建 TCP + 新建 SQLite 连接，且响应恒发 Connection: close

两个叠加效应：

  • 服务端不支持 HTTP keep-alive（每个响应都带 Connection: close）⇒ 面板每次轮询都要重新建 TCP。
  • 服务端每个请求新建一次数据库连接（全项目 44 处 _connect_db()）⇒ 每次都触发 WAL 的建/删文件。

在正常磁盘上这两件事都很便宜（对照实例 180 req/s、p95 196 ms 完全够用）； 但在你这台机器的用户目录里被放大成 6–8 倍（见 §2.1–2.2）。

建议：不动。生产在 Linux 上，当前数据量下完全够用，改连接池/keep-alive 属于架构改动、收益与风险不成比例。 真正该做的是把本地开发库挪出慢区（见 §2.2），一分钱不花、效果最明显。

低 · 记账两条「数据量再涨才痛」的地方
  • /api/v1/visits?pin=X（不带分页参数）会返回该顾问的全部历史，无上限。现在一个人几百条没事，攒到几万条时这一条响应会很大。带 page 参数则正常分页。
  • /api/v1/calls/export 一次性把整个结果集生成成 1.44 MB 字符串再返回，无流式。30 万行时单次约 30 MB 驻留内存。

现在都不构成问题，先记着。

说明本地压测验证不了限流

中继对 127.0.0.1 完全跳过限流（这是有意的，否则管理界面自己就被拦）。 所以本次压测没有覆盖到限流逻辑。线上真正的风险点是「同一办公室共用出口 IP」—— v4.21 已经按端点分级（认证类 60/min、轮询类 240/min、业务类 600/min）缓解过，这个结论本次无法验证，需要真机联网才能测。
