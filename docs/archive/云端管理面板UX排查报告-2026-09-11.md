## 0. 结论摘要

**一句话**：面板的视觉完成度很高（设计 Token 统一、图标规范、动效克制），但**"状态可信度"和"反馈闭环"是系统性的弱项**——大量地方"看起来正常、其实没连上/没保存/没导全"，而管理员没有任何线索去发现。这恰好击中了内部工具最怕的一点：**让人不敢信**。

**人机工程学上最贵的 10 个问题**（按"员工/管理员实际被坑的概率"排序）：

| # | 类别 | 问题 | 影响 | 位置 |
|---|------|------|------|------|
| 1 | 反馈闭环 | 网络/接口失败被伪装成"暂无数据"（`apiGet` 吞异常返回 `null`） | 分不清"真没数据"还是"坏了"，管理员会错误决策 | JS `1230-1236` |
| 2 | 反馈闭环 | 多处"保存类"操作 `catch{}` 静默失败（别名/姓名/分组） | 用户以为存了，刷新后"打回原形"，反复操作 | JS `1521`、`2063`、`2071` |
| 3 | 状态可信 | 令牌过期后**静默失联**：401 只在页面加载查一次，15s 自动刷新不看状态码 | 挂夜后次晨列表悄悄变空，无任何"请重新登录" | JS `2139-2145`、`1230` |
| 4 | 效率/干扰 | 自动刷新"太重"：每 15s 走 `refreshAll→showPage` 重建整表/整图 | 冲掉正在输入的内联编辑、丢失滚动位置；**且没有暂停开关** | JS `2107-2117`、`1113-1136` |
| 5 | 布局 | 数据表**无横向滚动容器**（`overflow-x`） | 手机管理(10列)/上门登记(11列) 在窄屏/小窗口严重变形 | CSS `168-172`、`255` |
| 6 | 数据正确 | 通话记录"导出CSV"**只导当前页 50 行且无提示**；与上门登记页的"全量导出"行为不一致 | 对账静默漏数据，比报错更危险 | JS `1582-1594` |
| 7 | 误导 | 设置页"保存设置"**是假的**（不发任何请求） | 管理员改了端口/日志级别以为生效 | JS `2101-2104` |
| 8 | 稳定性 | 后端 REST 限流 60 次/分钟/**IP** 会连带打到面板自己（**已实测触发**） | 面板自动刷新 + 人工浏览共享配额，超限即 429 → 叠加问题 3 变成"静默不更新" | 后端 `cloud_relay_v2.py:567` |
| 9 | 信息架构 | 无 URL 路由：**F5 就回首页**，无法收藏/分享具体页 | 高频页（上门登记）每次刷新都要重走一遍导航 | JS `1113` |

## 一、反馈与状态可见性（最伤人机体验的一类）

### 1.1 失败被伪装成"空"——这是最系统性的问题

`apiGet()`（`1230-1236`）把所有异常吞掉、返回 `null`：

```js
try { const r = await fetch(...); return await r.json(); }
catch(e) { return null; }
```

而各页面拿到 `null` 后的处理几乎都是"渲染成空/无数据"，**且不看 HTTP 状态码**：

| 页面 | 代码 | 失败时的表现 |
|---|---|---|
| 首页 | `if (!d) return;`（`1299`） | 静默什么都不做，"上次刷新"停止更新（无提示） |
| 首页客户端列表 | `if(!c \|\| !c.clients...)`（`1334`） | 显示"暂无客户端连接" |
| 通话记录 | `if(!d \|\| !d.calls...)`（`1544`） | 显示"暂无通话记录" |
| 人员管理 / 管理账号 | `catch{}`（`1183`/`2055`） | 显示"加载失败"（少数做对的） |
| 系统日志 | `if(!d \|\| !d.logs...)`（`1602`） | 显示"暂无日志"（**最危险**：以为服务没在跑） |

**人机风险**：管理员看到"暂无日志"，第一反应是"服务挂了"，而不是"接口 429 了"。

**建议**：包一层统一的请求层，区分三态——`ok / 空 / 失败`；失败时给橙色条 + 原因（HTTP 码 / 限流 / 过期），并给"重试"按钮。这是**投入最小、收益最大**的一项。

### 1.2 保存类操作静默失败

```js
async function setDeviceLabel(...) { try{...} catch(e) { /* 静默失败，刷新时自动同步 */ } }   // 1521
async function setPinGroup(...)    { try{...} catch(e) { /* 静默失败 */ } }                  // 2063
async function setAdvisorName(...) { try{...} catch(e) { /* 静默失败 */ } }                  // 2071
```

这三处是**内联编辑**（改设备别名 / 人员分组 / 顾问姓名）。网络抖动时：输入框内容还在（像成功了），下一次 15s 刷新把它冲回旧值——用户会以为是"面板自己有 bug"，而不是网络问题。

**建议**：`catch` 内补 `toast('保存失败，请重试','error')`；成功时给一句轻量 `toast` 或字段旁打勾（当前成功是**完全无反馈**的）。

### 1.3 令牌过期 → 静默失联

登录态只在**页面加载那一刻**校验一次：

```js
fetch(withToken('/api/v1/admin/accounts')).then(r => {
  if (r.status === 401) { clearSessionToken(); location.reload(); }   // 2139-2145
  ...
});
```

之后 15 秒一次自动刷新走的是 `apiGet`，**不看状态码**。管理员开会前打开面板、隔夜再来：所有列表悄悄不更新，**没有任何"请重新登录"提示**——因为 `if(!d) return` 把 401 也吃了。

**建议**：401 统一拦截 → 清 token → 弹登录框并说明"登录已过期，请重新登录"。

### 1.4 "假保存"与"提示像占位符"

设置页（`780-785`）的端口 / 日志级别输入框 + 保存按钮：

```js
function saveSettings() {
  document.getElementById('settings-msg').innerHTML =
    '<span class="msg-info">设置已保存提示（端口和日志级别需重启服务生效）</span>';   // 2102
  setTimeout(() => { ...清空... }, 4000);
}
```

不向任何后端发请求。而且文案里带"**提示**"二字，读起来就是没写完的占位符。

**建议（人机视角）**：这两个字段对"20 人单实例内部部署"根本不需要在 UI 暴露——**直接删掉整个"服务器设置"卡片**，比修好它更符合"减少误导面"。若保留，就接真实接口或标注只读并去掉按钮。

## 二、信息架构与导航

### 2.1 首屏状态被重复表达三遍

同一时刻的"服务状态"在首屏出现了 **3 处**：

- 侧边栏底部状态块：运行中·端口 / 运行时长 / 连接数（`499-502`）
- Hero 卡：云中继运行中 / 端口 / 已运行 / 当前连接（`539-551`）
- 顶栏：`自动刷新·每15秒` 徽章 + `上次刷新` + 刷新图标（`514-518`）

再加上 Hero 里还有一个"立即刷新"按钮（`547-550`）与顶栏刷新图标**功能完全重复**（`516`）。
→ 首屏最有价值的位置（顶部一条横幅高度）被重复信息占满，而真正的关键信息（哪台设备掉线了 / 今天谁没上报）反而要往下滚。

**建议**：状态只保留 **1 处**（推荐 Hero 卡）；顶栏只留刷新图标 + 主题 + 登录。侧边栏底部改成"当前页相关的快捷提示"或直接删。

### 2.2 没有 URL 路由 —— F5 就回首页

`showPage(id)`（`1113`）只切 class，**不写 `location.hash`**，也没有 `hashchange` 监听。
后果：管理员在"上门登记"页（高频页）按 F5 / Ctrl+F5 → **直接回到首页总览**，要重新点一遍侧边栏；也无法把某个页面收藏或发给同事。

**建议**：加 `location.hash` 同步 + 启动时按 hash 还原。改动量约 10 行，收益很高。

### 2.3 "系统日志"页塞进了整个统计分析

`page-logs`（`732-773`）里除了日志终端，还有：总消息数 / 上行下行流量 / 每日流量趋势 / 按 PIN Top10 / 每日明细表。
把一个"统计分析看板"藏进"系统日志"里，语义不符——管理员想找统计时不会去点"系统日志"。

**建议**：把统计部分独立成"运行统计"页，或并入首页。

### 2.4 筛选维度耦合（上门登记）

`visit-filter-pin`（业务员下拉）里塞了一个伪选项 `按分组筛选...`（`645`），选中后再把"分组"下拉显示出来（`1753-1757`），此时"业务员"下拉本身的值已经没有意义。
把两个正交维度（人 / 分组）耦合进同一个控件，用户理解成本高、且容易出现"我筛的是分组还是人？"的困惑。

**建议**：分组与业务员各占一个独立下拉，可同时生效（后端已支持 group 参数）。

### 2.5 主题菜单是"炫技项"

`THEME_LIST` 里有 10 个主题，含"赛博朋克 / 深空紫 / 冰蓝冷峻 / 极简白"（`910-921`）。
对一个公司内部管理后台，这是干扰项；且主题只存 `localStorage`，换电脑/清缓存即丢，多人协作时看到的面板长得不一样。

**建议**：保留 2 个（浅色/深色），其余收进"更多"。

## 四、一致性

反馈方式目前有 **三套并存**：

1. 全局 `toast()`（`1085`）
2. 局部 `form-msg` 文字（`showAdminMsg` `1223`、`settings-msg` `2102`）
3. 原生 `confirm()`（`1201`、`1786`、`2090`）

同样是"保存成功"：管理账号页用局部文字，设备别名用静默，添加账号用 Toast。
**建议**：统一到 Toast（瞬时）+ 行内校验错误（常驻），彻底移除原生 confirm。

其它小项：
- 术语混用："连接数" / "当前连接" / "总连接" / "在线手机" / 在线PC —— 同一概念多种叫法。
- 侧边栏"通话记录"用的是与品牌 Logo **同一个电话图标**（`492` vs `482`），识别度下降。
- `系统信息`卡片里"服务版本 6.0 (Sky Design System)"是**硬编码**的，与后端 `/health` 返回的 `4.10` 又是另一套（且后端那个也是写死的）——版本信息三处不一致，排障时会误导。

## 五、视觉 / 可读性 / 无障碍

### 5.1 字号偏小

| 元素 | 字号 | 位置 |
|---|---|---|
| 正文 | 13px | CSS `53` |
| 表头 | **11px** | CSS `259` |
| 小按钮/次要文字/辅助列 | **11px** | CSS `250`、`274` |
| 筛选标签 | 11px | CSS `319` |

在一台 1080p/2K 屏上长时间值守，11px 的表格头与次要列（模型/版本/最后活跃）阅读负担偏重。
**建议**：表头 → 12px，次要文字 → 12px，正文 13→14px。

### 5.2 对比度不达标（实测计算）

| 组合 | 近似对比度 | WCAG AA(普通文字 4.5:1) |
|---|---|---|
| 次要色 `#5880A8` on 白底 | **≈ 4.1 : 1** | ✗ 不达标 |
| 同上 on 面板底色 `#EBF4FF` | ≈ 3.9 : 1 | ✗ |
| 输入框 placeholder（`text-2` + `opacity:.7`，`308`） | ≈ 2.9 : 1 | ✗ 明显不足 |
| "离线"徽章：`#5880A8` on `#D8ECFC`（`293`） | ≈ 3.4 : 1 | ✗ |

这些恰好都用在了**需要被读到的地方**（表头、次要列、占位提示、离线状态）。
**建议**：`--text-2` 加深到约 `#41648A`（≈4.8:1）；placeholder 去掉 `opacity`。

### 5.3 其它

- `.empty-state .icon`（`407-408`）定义了空状态图标样式，但全站空状态**都只用了纯文字**——空状态设计没落地。
- 未处理 `prefers-reduced-motion`，而页面有多处动效（`fadeIn`、`pulse` 无限脉冲、卡片 hover 位移）。
- 浅色主题下"系统日志"是一整块深色终端（`#0D1526`，`392-403`），视觉上很突兀——作为终端块可以接受，但建议降低高度或做成可折叠。
- 表格 `td-ellipsis` 依赖 `max-width` 生效，而 `table-layout` 为默认 `auto`，**截断不一定生效**，长 device_id 可能撑破列宽。

## 六、响应式 / 移动端

- `@media 1100px` 侧边栏收成图标条、`768px` 变抽屉（`454-474`）——导航部分做得不错。
- **但表格没有任何横向滚动容器**（`.card` 与 `.data-table` 都没有 `overflow-x`）。10~11 列的表格在 <1100px 时列会被强行挤压换行，768px 以下基本不可用。
- 顶栏在窄屏仍同时显示：自动刷新徽章 + 刷新图标 + 主题 + 登录按钮（`471-472` 只隐藏了"上次刷新"文字），存在拥挤/溢出的可能。
- 管理员用手机/平板临时看数据是这个面板的真实场景之一（尤其"上门登记"），建议优先补 `overflow-x:auto` 包裹。

## 七、已核实"**不是**问题"的项（避免后续重复排查）

1. **时间不存在 8 小时偏移（原 D-4 排除）**。
   线上实测：服务器时区 `Asia/Shanghai (CST, +0800)`，`date` 与 Python `datetime.now()` 输出一致（均为北京时间 14:36）。后端 naive 时间**就是北京时间**，前端 `toLocaleString('zh-CN')` 显示正确，"今日"统计边界也正确。→ **无需改动**。
   （唯一的隐患是"依赖服务器时区配置"，未来若迁移到 UTC 实例才会出问题，可记为长期项。）

2. **35430 前面没有反向代理（原 C-6 的"反代截断"当前不成立）**。
   实测 `0.0.0.0:35430` 由 python3 直接监听，1Panel 的 openresty 容器并未转发该端口。所以批量导入走 GET query 目前不会被 Nginx 截断。
   但仍有两点保留：① 长 JSON 明文进访问日志；② 若将来在面板前加反代（HTTPS/域名），8KB URL 上限会立刻变成真问题。建议仍改为 POST + body。

3. **面板"系统日志"页的日志顺序正常**。
   `get_logs()`（`1225`）读取的是 `RotatingFileHandler` 写出的 `cloud-relay.log`（带日期 `[%Y-%m-%dT%H:%M:%S]`、10MB×5 轮转），**不是** supervisor 的 stdout 日志（后者只带 `[HH:MM:SS]`、跨天不单调）。日志页显示是正常的。

## 八、顺带发现的运行时问题（会影响面板观感与排障）

### 8.1 【新，真实存活 BUG】`list | list` 必然抛异常

`cloud_relay_v2.py:868`（当前部署版本，已确认在线上日志中多次出现）：

```python
for w in list(group.pcs) | list(group.phones):      # TypeError: unsupported operand type(s) for |: 'list' and 'list'
```

`group.pcs` / `group.phones` 是 `set()`（`488`），但这里先 `list()` 再 `|` → `list | list` 直接抛 `TypeError`。原意应是 `list(group.pcs | group.phones)`。

**触发条件与影响**：该分支在"**非首设备加入已有组**"时执行（`867`，即 手机连一台已经在线的 PC —— 也就是**最正常的使用场景**）。异常会中断整个协程，导致：
- "新设备加入"(`new_device_join`) 通知**发不出去**（PC/其他设备界面不会提示有新设备接入）；
- 该分支之后的逻辑全部跳过；
- 日志被 `Connection error: ...` 刷屏。

线上日志佐证：`ERROR` 17 次、`Traceback` 23 处，其中包含该异常（历史行号 435，现为 868，说明**这个 bug 跨版本一直存在**）。

**建议**：改为 `for w in list(group.pcs | group.phones):`，一行修复。

### 8.2 Linux 上每次启动都报"防火墙规则失败"（噪音）

`configure_firewall()`（`1132-1171`）硬编码调用 Windows 的 `netsh`，在 Ubuntu 上必然失败并打 `ERROR 添加防火墙规则错误: ... 'netsh'`。服务本身不受影响，但**污染日志**，会掩盖真错误。
**建议**：加 `if sys.platform != 'win32': return`。

### 8.3 限流实测数据（验证了 8.2-① 的推论）

线上日志统计：`RATE_LIMITED` 共 **227** 次。

| 维度 | 数据 |
|---|---|
| 按 IP | `36.28.161.172` **179** 次；其余 `125.120.251.86` 19 / `58.101.35.194` 10 / `36.28.139.192` 8 / `211.90.237.216` 6 / `183.137.36.52` 5 |
| 按端点 | `/api/v1/visits` 55、**`/api/v1/dial` 55**、`/api/v1/calls/batch` 52、`/api/v1/status` 10、`/api/v1/auth/pending` 9、`/api/v1/pins` 5、`/api/v1/groups` 3 |
| 时间 | `36.28.161.172` 的 179 次**全部集中在今天 14 点这一小时内** |

**判读**：今天 14 点这一批，时间点与本地 `test_stress_live.py`（今天 14:09 修改、且脚本明确设计为"从真实外网 IP 打、专测 60/min 限流拐点"）吻合，**判定为你本人跑压测造成的**，不是员工日常。
但两点仍然成立并值得处理：
1. 它**实证**了"整个办公室共用一个出口 IP 时会撞 60/min 限流"——这正是 `visits/dial/calls-batch` 这三类**业务端点**被限流的表现，员工会直接体感为"拨不出去 / 登记失败 / 通话记录对不上"。
2. 面板自身的自动刷新（15s 一次）与人工浏览，**和员工共用同一份 60/min 配额**；一旦超限，叠加"问题 1.3 静默失联"，面板就变成"看着正常但不更新"。
3. 另有 `RATE_LIMITED phone_hello`（WS 握手限流）在若干 IP 上**成簇出现**（同一秒 4~5 条），像是**客户端重连风暴**——设备被限流后立即重试，越试越被拦。

**建议**：严格限流只留给认证敏感端点（login / PIN 尝试）；业务端点（dial / visit / calls-batch / events-log / pins）改为按 **PIN/设备维度**限流，或把阈值抬高到 600/分钟/IP。
