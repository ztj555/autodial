## 遗留问题回顾

| # | 问题 | 后果 |
|---|---|---|
| B | 手机端 `deviceName` 用 `Build.MODEL`（设备型号），云端以它作设备唯一键绑定 default_pin | 同型号多台手机共享同一绑定，互相污染；换配对码触发授权流程 |
| A | 手机端不处理 `auth_pending`（等待浏览器插件授权） | 等待期间 UI 无提示干转圈，120 秒超时后报"连接被拒绝：授权超时"，用户误以为配对码错误 |

优先级：**B 先做**（身份错乱是"莫名被拒"的主要来源），A 后做（体验补全）。

## 修复 B：设备唯一标识 deviceId

### 设计原则
- `deviceName` 保留为**展示名**（型号），新增 `deviceId` 作为**唯一键**（型号 + ANDROID_ID 后 6 位）。
- 云端绑定、查询、去重全部改用 `deviceId`；所有面向用户的消息（auth_pending / auth_ok / 日志展示）继续传 `deviceName`。
- 对 PC 端零破坏：云端转发 phone_hello 时本来就有 `msg['deviceId']` 字段（Bug6 修复），PC 端已按 deviceId 识别设备。

### B1. 手机端 —— `ConnectionManager.kt`

两处 hello 均改（LAN 约 776 行、Cloud 约 917 行）：

```
现在:  put("deviceName", Build.MODEL ?: Build.DEVICE ?: "Android")
改为:  put("deviceName", <型号，不变>)
       put("deviceId",  <型号>-<ANDROID_ID 后 6 位>)
```

- `ANDROID_ID` 取 `Settings.Secure.ANDROID_ID`（ConnectionManager 构造已有 context）。
  Android 8.0+ 该值与 app 签名绑定，卸载重装不变、恢复出厂才变，符合"设备身份"语义。
- 正常设备有后缀；取不到时回退纯型号（等同旧行为，不会更糟）。
- ConnectionManager 已有 `deviceId` 概念可复用，注意 LAN/Cloud 两处保持一致，建议提取为一个 `resolveDeviceId()` 私有方法，避免两处逻辑漂移。

### B2. 云端 —— `cloud_relay_v2.py` phone_hello 区（约 670-700 行）

```
device_id   = msg.get('deviceId') or msg.get('deviceName')   # 向后兼容旧 APK
device_name = msg.get('deviceName', ...)
```

- `_get_device_default_pin(device_id)`、`_set_device_default_pin`、踢旧连接、组内广播等**一律用 device_id**。
- `AUTH_DENIED_NO_DEFAULT` / `AUTH_DENIED_EXT_OFFLINE` / `AUTH_REQUEST` 日志改打 `device={device_id}`。
- auth_pending / auth_ok 消息体中 `device_name` 字段不变（手机 UI 展示用）。
- 转发给 PC 的 `msg['deviceId']` 由现在的型号改为 device_id（更精确）。

### B3. 存量数据迁移（关键，否则升级后所有手机首连都会"未在云端注册"）

新 deviceId 在 `phones` 表无记录 → default_pin=None → 按设计拒绝。两个迁移选项：

- **选项 a（推荐）**：管理后台对每台设备按新 deviceId 重新预设默认 PIN。干净、顺带清理历史上同型号污染的脏数据。
- **选项 b（兜底）**：一次性 SQL 把 `phones` 表中 `device_id = '纯型号'` 的记录改名为 `'型号-ANDROID_ID后6位'`。**仅当该型号只登记过一台手机时可用**；历史上已污染的多台无法区分，必须走选项 a。
- 管理后台设备列表如需支持展示 deviceId / 新增预设入口，列入后台小改动。

### B 的兼容性
- 旧 APK（无 deviceId 字段）连新云端：回退 deviceName，行为与现在完全一致，零破坏。
- 新 APK 连旧云端：多发的 deviceId 字段被旧云端忽略，零破坏。
- 可灰度：先发云端，再发 APK。

## 修复 A：auth_pending 授权等待体验

云端事实（已确认）：授权通过后云端直接向手机原 ws 发 `auth_ok`（927、1895 行），超时/拒绝发 `auth_fail`。**手机端现有 auth_ok / auth_fail 分支都能接住，缺的只是"等待中"的中间态展示。**

### A1. `ConnectionManager.kt` — Cloud listener `when` 新增分支

```
"auth_pending" -> {
    // 记录 request_id（可用于诊断日志）
    handler.post { notifyMessage(msg) }   // 走现有 notifyMessage 通路
}
```

### A2. `DialService.kt` — 消息监听器新增 auth_pending 处理

仿照现有 `ACTION_SHOW_SMS_CONFIRM` 广播模式：

- 收到 `auth_pending` → `sendBroadcast(ACTION_AUTH_PENDING)`，附带 `message` / `default_name` 字段。
- 不调用 `notifyConnectionChange`（它的语义是"已断开"，会误触发重连/状态栏逻辑）。

### A3. `ConnectFragment.kt` — 注册广播接收 + UI

- 显示：`等待授权中…（{message}）`，状态点黄色/脉冲，按钮文案改为"取消"。
- 用户点"取消"：复用现有 `sendDisconnectCommand()` 即可，云端 `finally` 已有 `_pending_auths` stale 清理（1033 行），无残留。
- 超时路径无需新代码：120 秒后云端发 `auth_fail '授权超时（120秒内无响应）'`，v4.15 的 reason 透传已能把它正确显示为"连接被拒绝：授权超时…"。

### A 的范围界定
- LAN 侧无授权流程，不动。
- 不新增 `ConnectionState` 枚举值，避免波及状态机与通知逻辑（用广播+UI 呈现，侵入最小）。

## 回归测试清单

1. **同型号两台手机**分别用不同 PIN 连接同一云端 → 各自绑定、互不污染（B 验收）。
2. 同一台手机**换 PIN**（绑定 PIN 之外）→ 插件在线时收到 auth_pending → 授权后 auth_ok 正常进入；插件离线时提示"浏览器插件未激活"。
3. 授权等待期间：UI 显示等待提示；点取消能退出；放任 120s → 显示"授权超时"。
4. **旧 APK + 新云端**：行为与升级前一致（deviceId 回退）。
5. **新 APK + 旧云端**：行为一致（多余字段被忽略）。
6. 云服务器列表多个条目时，auth_pending 只在目标服务器上生效，切换下一个服务器逻辑不受影响。
7. LAN 直连回归：UDP 发现、配对成功/失败提示不受影响。
