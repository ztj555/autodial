## 二、跨端系统性问题（4 条主线）

这 4 条不是单点 BUG，而是贯穿多端的设计矛盾，建议优先决策。

### 主线 1：安全加固把"局域网直连"这个便捷性功能悄悄打死了

- PC 端（Electron）`main.js:830`：`server.listen(PORT, '127.0.0.1', ...)` —— 只监听回环地址
- PC 端（Electron）`modules/server.js:50,55-88`：要求回环 Host + 可信来源，注释明确写"端口仅绑定 127.0.0.1"
- PC 端（Go）`server.go:260`：`Addr: fmt.Sprintf("127.0.0.1:%d", Port)`，`devices.go` 的 WS `CheckOrigin` 同样拒绝非回环 Host
- 但 Android 端**一直在尝试局域网直连**：`ConnectionManager.kt:59` `LAN_PORT = 35432`、`ConnectFragment.kt:588` UDP 局域网发现、`ConnectionStrategySheet.kt:22` "仅局域网：只连接同一局域网内的电脑"
- **后果**：手机端"自动(局域网优先)"和"仅局域网"两种策略实际都无法建立本地连接，永远退到云中转。更糟的是 `ConnectFragment.kt:391` 还在提示"④ 连不上时检查电脑防火墙是否放行端口 35432"——**这不是防火墙问题，是 PC 根本没监听局域网**，用户按提示操作只会白费功夫。
- **决策建议**：二选一，别停在中间态。
  - 若保留局域网直连：PC 改绑 `0.0.0.0`，`CheckOrigin`/来源校验改成"同子网 + 已配对 PIN 放行"，并同步修正 README 与手机端提示文案；
  - 若确定只走云端：从手机端 UI 移除"仅局域网"策略、移除 UDP 发现与相关提示，避免误导。（此路更省事，且 20 人规模走云端完全够用）

### 主线 2：状态显示与实际不一致（"看着连上了，其实没连"）

多处界面状态字段与真实状态不同源，员工会据此做错误判断：

- Electron `main.js:472-482` 的 `get-info` **不返回 `connected` 字段**，但 `renderer/index_temp.js:113` 判断的是 `if (info.connected)` → 启动后状态位永远是"未连接"，直到下一次事件才更新
- Android `CloudServerSheet.kt:94-96` "设为当前"只写 SharedPreferences + 刷新 UI，**不触发断线重连**（详见 A-2）
- Go `server.go:265-272` 端口被占用时只写日志，托盘不变红、无弹窗 → 坐席完全无感知

**统一建议**：所有"已连接/在线"状态必须由**唯一数据源**（连接管理器实时状态）驱动，页面首次加载时主动拉取一次真实状态，禁止用"事件推送才会更新"的默认值糊弄首屏。

### 主线 3：失败被静默吞掉，用户"点了没反应"

这是最伤便捷性的一类问题——用户不知道发生了什么，只能反复点。

| 位置 | 现象 |
|------|------|
| Electron `main.js:536` | `if(!network.isValidDialNumber(...)) return;` 号码不合法直接 return，**零反馈** |
| Electron `modules/server.js:130` | 同上，HTTP 拨号端点号码校验失败无明确返回 |
| 扩展 `background.js:218-226` | PC 端 `/dial` 返回非 2xx 时**不报错**，静默穿透去走云端（见 E-3，可能双拨） |
| Go `server.go:265-272` | 端口占用静默失败 |
| Android `StatsFragment.kt:571-577` | 同步失败只提示"请检查云端连接"，不带错误码/服务器信息 |

**统一建议**：凡是用户主动发起的动作，失败必须给出**可操作**的反馈（原因 + 下一步），而不是 return / catch{}。

### 主线 4：云端所有 REST 请求都会阻塞 WebSocket 事件循环

- `cloud_relay_v2.py:1412` `health_check_handler` 的 docstring 明确写"同步 DB 查询通过 `_db_executor` 线程池卸载"
- 但实际代码里，`_connect_db()` + `cursor.execute()` 是**直接同步调用**（L1469、L1503、L1676、L1703、L1728… 全部如此），**并没有** `run_in_executor`
- 对比 `phone_hello` 中的写法（L818、L852）——那里是正确的 `await loop.run_in_executor(_db_executor, ...)`
- 该函数由 `_PeerProtocol._process_request_with_peer`（L592-598）以 `await health_check_handler(...)` 方式调用，即**运行在 asyncio 事件循环上**
- **后果**：任何 REST 请求执行期间（尤其是 `/api/v1/visits/export` 这种可能扫 20 万行的大查询），**所有 WebSocket 的心跳与拨号指令被冻结**。20 人同时在线时，一次导出就能让全员卡顿。
- **建议**：把 `health_check_handler` 内所有 DB 访问统一包进 `await loop.run_in_executor(_db_executor, ...)`（照抄 `phone_hello` 的写法），并对导出接口限行/流式返回。这是"云端稳定运行"的最关键一项。

## 五、复核说明：已确认**不是**问题的项

为避免误导，以下原被怀疑、经回源码核实后**判定为非缺陷**，无需改动：

1. **"PC 端收到 ping 不回 pong 导致约 90 秒断开"——不成立。**
   云中继 `cloud_relay_v2.py:1050-1067`：手机发来的 `ping` 会被附加 `deviceName` 后转发给 PC，并由服务器（L1066）直接回 `pong` 给手机；PC 自己发的 `ping` 命中 `PHONE_TO_PC_TYPES`（L602 含 `'ping'`）同样在 L1065-1066 得到 `pong`。Electron `modules/cloud.js:235-238` 收到 ping 只更新心跳、不回 pong，是**正确**的——需要 pong 的是发起方（手机），不是 PC。
   （另：服务端 `ping_interval=30`、`ping_timeout=90` 使用的是 WebSocket 协议级心跳，`websockets` 库会自动应答，与此无关。）

2. **云中继 `websockets>=12` 未锁上界——当前不会导致启动失败。**
   `websockets.legacy.server` 自 14.0 起弃用但从未移除，实际可导入。属**防御性**建议（钉死 `<14`），非现存 BUG。

3. **扩展端 11 位手机号识别——正常，无需改动。**（已按你的更正调整：E-2 仅保留"CRM 改版时的选择器健壮性"，且不涉及座机/分机扩展。）

4. **Android 无障碍服务——仅部分小米机型需要，其余机型不需要。**（已按你的更正调整：A-1 改为"设置页增加开关"，严重度下调为 P2。）

5. **Android `visit_records` 会被"以云端为准"覆盖——设计如此，但需加空值保护。**
   代码注释明确写了这是有意为之（L541），不算误写；风险点仅在于**空数组/空结果也执行覆盖**（已在 A-3 单列）。

> 说明：第 3.2 节中 **C-3（单 PIN 未鉴权读取）** 属安全范畴，按你"便捷性优先"的取向，可排在功能修复之后；但它是**改动成本最低**的一项，建议顺手处理。

## 八、20 人同时使用的承载能力评估

**一句话结论：正常办公时段能扛住，但有 3 个"临界点"在特定场景会翻车；其中最可能先出问题的是云端 REST 限流，而现有压测恰好测不到它。**

### 8.1 规模基数（先看余量，都是够的）

| 项目 | 现状 | 20 人时占用 | 结论 |
|------|------|------------|------|
| WS 连接数 | 压测已验证 100 连接 | 20 手机 + PC/扩展 ≈ 25~30 | 余量充足 |
| 连接队列 `max_queue` | 128 | 远未触及 | 充足 |
| DB 专用线程池 `_db_executor` | 8 线程 | — | 够用（但注意它当前几乎没被 REST 用上，见 C-1） |
| 默认线程池 | 32 线程 | — | 对 REST 阻塞**无帮助**（见 8.2-②） |
| SQLite | WAL + `busy_timeout=5000` | 写并发低频 | 设计正确 |
| 同 PIN 手机数 | 只允许 1 台（踢旧机） | 每人 1 PIN，互不干扰 | 不会互相顶掉 |

### 8.2 三个必须知道的临界点（按"先出事"排序）

**① REST 限流 60 次/分钟/**IP**，在同一出口 IP 下被所有人共享 —— 最可能先翻车的点**

- `cloud_relay_v2.py:567` `MAX_REST_PER_MINUTE = 60`，按**客户端 IP** 计数（`check_rest_rate_limit`）。
- 手机端每 5 分钟上报 3 个 REST 请求（`DialService.kt:841` 定时 + `:887` calls/batch + `:912` stats/report + `:930` events/log）。
- **关键场景**：20 台手机若都在公司 WiFi 后面（同一公网出口 IP），再加 PC 扩展的登记/拨号、管理面板 **每 15 秒**刷新（`dashboard.html:872`）——**早高峰集中上线、断网重连的突发**，一分钟内很容易越过 60 次 → 服务器直接返回 `429 RATE_LIMITED` → 员工表现为"**拨不出去 / 登记失败**"。
- ⚠️ **现有压测测不到这个问题**：`test_stress_50_users.py` 从 `127.0.0.1` 发起，而代码对 localhost 是**豁免限流**的（`cloud_relay_v2.py:572`）。所以"50 并发全通过"**不能**证明线上 20 人也能通过。
- **建议**：把严格限流**只用在认证敏感端点**（login、PIN 尝试），业务端点（dial / visit / calls/batch / events/log…）改为**按 PIN/设备维度限流**或大幅提高阈值（如 600/分钟/IP）。

**② REST 的同步 DB 操作阻塞事件循环 —— 平时无感，重负载时全员卡顿**

- 见"主线 4"/C-1：REST 处理函数在**事件循环**上直接跑同步 SQLite。
- 本次补充了决定性证据：websockets legacy 的 `process_request` 若返回协程，是**直接在事件循环上 `await`** 的（官方 12.0 源码用 `isinstance(..., Awaitable)` 判断后 `await`，**全程没有 `run_in_executor`**）。因此 `cloud_relay_v2.py:2946` 那句"扩大默认线程池防止 sync process_request 排队超时"的**前提是错的**，调大线程池对 REST 阻塞没有任何帮助。
- 平时每次查询只有几毫秒，20 人感觉不到；但 `visits` 表涨到几十万行后，或管理员点"导出 / 大范围查询"（`/api/v1/visits/export` 上限 20 万行，`:2551`）时，单次同步查询可能数百毫秒~数秒，期间**所有手机的 WS 心跳与拨号指令被冻结**。20 人同时在线时体感最差。
- **建议**：C-1 的修法（统一 `run_in_executor`）是这项的唯一正解。

**③ 批量通话记录走 GET 查询串，反代下可能被截断**

- C-6：`/api/v1/calls/batch?data=<大段JSON>` 用 GET+query。若云端前面有 Nginx / 1Panel 反向代理，URL 长度常见上限 8KB，**大 JSON 会被截断或直接 414**。
- 手机每 5 分钟一批，通话多时批量会变长 → 上报失败、对账缺口。
- **建议**：改 POST + body；若短期难改，确认反代 `large_client_header_buffers` 并给手机端加"单批条数上限"。

### 8.3 不会出问题的部分（可以放心）

- 同 PIN 只保留一台手机（`phone_hello` 踢旧机设计），不会出现"20 台手机互相顶掉"。
- WAL 模式已解决"写锁阻塞读"；`busy_timeout=5000` 已覆盖跨连接写冲突。
- 连接数、消息队列、内存结构（有 `cleanup_memory` 周期清理）都远未到阈值。

### 8.4 建议的验证方式（可操作）

1. **压测要"从非本机 IP 打"** 才能覆盖限流；或临时把 `MAX_REST_PER_MINUTE` 调大再压一次。
2. 上线后**盯日志关键词**：`RATE_LIMITED` / `429`。若出现，说明 8.2-① 已经发生。
3. 用**较长周期**观察 `visits.db` 行数；一旦进入十万级，优先做 C-1。
